# Architecture

`ast-bro` is a fast, structurally-aware code-navigation toolkit. It started as a "shape extractor" (signatures with line ranges, no method bodies) and has grown into eight orthogonal subsystems sharing one binary, one filter pipeline, and one walk infrastructure:

1. **`src/adapters/` + `src/core.rs`** — language adapters parse files into a shared `Declaration` IR; renderers turn that into `map` / `digest` / `show` / `implements` output.
2. **`src/surface/`** — resolves the *true public API* of a package (`pub use`, `__all__`, TypeScript barrels, Scala `export`) instead of just listing every public item per file.
3. **`src/deps/`** — file-level dependency graph (`deps`, `reverse-deps`, `cycles`, `graph`) for nine languages. See [deps.md](deps.md).
4. **`src/calls/`** — symbol-level call graph (`callers`, `callees`) for all 14 languages, with a three-pass resolver (same-file → global symbol table → dep-graph disambiguation). See [calls.md](calls.md).
5. **`src/impact.rs`** — cross-file impact analysis (`impact`): callers + callees + file reverse-deps + test detection bundled into one "blast radius" report, with `--mode {deps,dependents,tests,all}` and `--tests` / `--exclude-tests` filters. See [impact.md](impact.md).
6. **`src/context.rs`** — token-budgeted context pack (`context`): greedy knapsack that assembles "everything the agent needs to understand symbol X" into a caller-supplied token budget. Works for both callable and type targets (type targets include implementors, methods, and method dependents). See [context.md](context.md).
7. **`src/search/`** — hybrid BM25 + dense semantic search, plus `find-related`. Cached at `.ast-bro/index/`. See [search.md](search.md).
8. **`src/squeeze/`** — reversible token compression for **logs/text** (`squeeze`): a multi-stage pipeline that shrinks repetitive lines and emits a legend so the output round-trips back to the original. Not a code tool — for code, the "compression" is `map` / `digest` / `show`. See [squeeze.md](squeeze.md).

The dep graph and call graph share one on-disk cache at `.ast-bro/deps/graph.bin` (`UnifiedGraph { deps, calls: Option<CallGraph> }`) and one process-wide `Arc<UnifiedGraph>` registry in `src/graph_cache/` so MCP `tools/call`s reuse a single parsed copy across the whole session. `impact` and `context` both ride on that same unified cache.

It is written natively in Rust, relying heavily on the [tree-sitter](https://tree-sitter.github.io/tree-sitter/) parsing framework via the excellent [`ast-grep`](https://ast-grep.github.io/) ecosystem bindings, achieving incredibly fast speeds while still taking advantage of `rayon` for massive multithreading across directories. The walking subsystems all share `src/file_filter.rs` for what gets walked (see [file-filtering.md](file-filtering.md)) — adding a feature in one subsystem doesn't change what files the others see. (`squeeze` is the exception: it reads one explicit file path directly, so it neither walks nor touches the filter pipeline.) `file_filter.rs` also hosts `is_test_file` (test-file heuristics used by `impact`, `callers`, `reverse-deps`), `detect_language` (shebang-based language detection for explicitly-passed extensionless files), and `file_identity` (the `canonicalize`-based key that makes overlapping walk roots name each file once — see [file-filtering.md](file-filtering.md#overlapping-roots)).

## Core Flow (shape commands)

1. **Routing (`src/main.rs`)**: `ast-bro` iterates through files using the `ignore` crate (which handles `.gitignore` automatically in parallel). Each file extension is identified by `ast-grep`'s `SupportLang::from_path(path)`.
2. **Parsing (`src/adapters/*`)**: The raw source string is handed to `ast-grep` which returns a tree of `ast_grep_core::Node`. A language-specific adapter (e.g. `rust.rs`, `python.rs`) performs a highly tailored AST traversal over these nodes.
3. **IR Generation (`src/core.rs`)**: The traversal emits a canonical `Declaration` tree. This is the Intermediate Representation (IR) shared across every language. It encapsulates `kind`, `name`, `signature`, `docs`, `visibility`, etc.
4. **Rendering (`src/core.rs`)**:
   - `map` iterates the declarations to print a hierarchical file breakdown.
   - `digest` squashes the tree into a concise module-level API map.
   - `show` walks the tree for a specific suffix match and extracts the raw string boundaries. Target resolution and rendering live in [`src/show.rs`](../src/show.rs), shared by the CLI and the MCP tool so the two cannot drift: a target is a file, a directory, or a quoted glob, and `show::partition` decides where the target list ends and the symbol list begins by asking the filesystem rather than by argument position. That is what recovers an unquoted glob — the shell expands `show src/*.cs Widget` before the process starts, and the extra files used to land in the symbol slot, resolving the symbol against the first file alone and silently dropping its other definitions at exit 0. Explicitly named files are parsed directly (a file you typed is a file you want, ignore rules notwithstanding); directories and globs go through `walk_and_parse`, so they honour the same filter pipeline as `map`. Multi-file answers carry a coverage header and a `--limit` display cap; a single explicit file keeps its historical uncapped, headerless output.
   - `implements` performs a generic Breadth-First-Search across the IR trees of the entire repository to find inheritance hierarchies. The walk is only as good as its edges, so target resolution and the edge resolver live in [`src/implements.rs`](../src/implements.rs), shared by the CLI and the MCP tool. A supertype is written as a name, and two packages can declare the same name: matching on the simple name merges the two declarations, and every subtype of one is then reported as a subtype of the other — in pgjdbc the interface `org.postgresql.api.codec.TextCodec`, which never reaches `BinaryCodec`, contributed three of the 52 types that `implements BinaryCodec` used to report, because the unrelated class `org.postgresql.jdbc.codec.TextCodec` does. `_resolve_base` therefore resolves a name in priority order. A rename the referring file introduced (`import a.b.Base as Alias`) comes first and is decisive, because it is local and explicit and shadows any declaration of that name elsewhere — bounded by its own scope, which the extractor does not record but the import's line and the namespace's line range recover between them, so a `use … as …` inside one Rust `mod` is not in scope in its sibling. It shadows that declaration whether or not the walk holds what the rename names, which is the half that took two rounds to get right: an external dependency is normally outside the walk, so reading "the rename resolved to nothing" as "there was no rename" sent `import com.external.Thing as Widget` on to whatever unrelated `Widget` the walk happened to declare. Unresolved but bound is still bound, and the same holds for a rename that binds the *head* of a qualifier: `use external::stuff as api` makes `api::Handle` mean `external::stuff::Handle` and nothing the walk declares under some other module. A reference the walk cannot follow is then reachable from the other side, by the name it really spells — `implements external.stuff.Handle` finds it — since suppressing an edge under the wrong name is only half an answer if the right name cannot find it either. C# is the exception the other way: it looks in the enclosing namespace before its using aliases, where Kotlin, Rust and Scala look at the import first. A qualifier comes next: a reference that spells one out means the type it names or nothing, so `implements java.lang.Runnable` written where the walk happens to declare an unrelated `mylib.Runnable` is not an edge to it — and that has to hold with one candidate as much as with two, since a lone candidate is exactly where a merge has nothing to make it visible. It rules a declaration *out*, though, only in a language whose modules are declarations rather than files: in Python, TypeScript and Rust `api.Base` is as likely a module alias as a package path, and rejecting on a comparison that cannot be made deleted the edge and reported nothing. The test is the language and not an empty package string — a Java file in the default package has no package clause and is still Java, and reading that as "no namespace syntax" brought the merge straight back. For the same reason an edge never crosses a language at all: a Java `extends` clause cannot name a TypeScript interface, whatever the two call themselves, though a *target* may legitimately span languages and the name index is therefore language-blind. A leading segment that some import of the referring file binds is expanded first, whether the import renames the type (`using Api = Example.Other;`) or simply names an enclosing one — `import org.example.TestClass` makes `TestClass.Nested.Sub` absolute, and without that the partial spelling reads as a trailing run of any same-shaped nesting, so two such types in different packages were reported ambiguous when an import had pinned one all along. A qualifier that still fits several declarations narrows rather than decides, leaving the reference to the rules below. Both sides of that comparison are spelled in one alphabet: a namespace can be several segments in a single declaration — PHP's `namespace App\Base`, C++17's `namespace A::B` — so a declaration's own qualified name is split on the separators a reference is split on. Reading it as one segment made `class Child extends \App\Base\Root` agree with nothing, and a rule that rejects every candidate leaves no ambiguity to report, so the edge disappeared in silence on essentially every PSR-4 project. Below those the rules are *narrowings* over the declarations carrying the simple name — the referring file itself, a single-type import, the referring file's package, an on-demand import — each applied only when it leaves a candidate standing. A name that is unique in the walk resolves on the last rule alone, so the rules can only change an answer that was a guess to begin with. The two import rules sit either side of the package rule because that is where the languages put them: a single-type import shadows a same-named type from the file's own package (JLS 6.4.1) and a wildcard does not. Imports come from `deps::extract` — the extractor the dep graph already uses, rather than a second one that could disagree with it — and each file is extracted at most once per query. What extraction is *not* gated on is the name collision that motivated the index. The rename rules ask first whether a file could rename an import at all, and since a rename outranks the declaration index they run before it, so in a language that can rename every reference in such a file pays; the qualifier expander and the two import narrowings ask nothing and extract whenever they run, which is a reference spelling more than one segment or a simple name two declarations carry. A Java tree therefore extracts too, on exactly the queries the resolver exists for. The cost is about a `map` plus a `deps` extraction over the same tree — 1.5s against 0.3s over 550 Python files of ~7 KB. Keying the probe on the name the reference spells would be cheaper and is the wrong trade: a false positive costs one reparse, a false negative deletes an edge and reports nothing. What survives is either one declaration (an edge) or several (no edge, since guessing would attach a subtype to a hierarchy it has no relation to). A dropped edge is reported, not silent: `ambiguous` in JSON, a `# note:` on stderr, and the same line on the MCP body, which is the treatment truncation and depth cutoffs already get. The target goes through the same resolution, so `implements jdbc.codec.TextCodec` answers for one declaration and a bare `implements TextCodec` answers for both and says so. A target the walk does not declare is the ordinary case rather than an error — `implements Runnable` over an application tree means the JDK's — so the references that spell that name are the answer; how much a reference has to spell depends on what the walk can say, and where it declares the name and the qualifier rejected every declaration, only an agreeing qualifier counts. That is what keeps `implements no.such.TextCodec` a rejection (exit 2) while `implements java.lang.Runnable` still answers next to an unrelated `mylib.Runnable`. A bare out-of-walk target can cover two spellings that name different types, and reports which ones it merged. Languages with no namespace syntax (Python, TypeScript) never reach the package rule and resolve on imports alone; a relative specifier such as `./base` is resolved against the referring file, so it names one file rather than every file with that stem. All of this only matters where the adapter records supertypes at all, and every adapter that has a supertype clause now does — Java, C#, Kotlin, Scala, Go, Rust, Python, TypeScript, JavaScript, PHP, C++ and Ruby, guarded by a per-language fixture so a language cannot go quiet again. Rust is the one partial case: it records `impl Trait for Type` but not a supertrait bound (`trait Base: Root`), which therefore produces no edge. Ruby records only `<`; a mixin brought in with `include` is not a recorded supertype, though Ruby's own `is_a?` says otherwise. A superclass Ruby computes (`< Struct.new(:a, :b)`, `< Data.define(:x)`) is recorded as written and resolves to nothing, which is the answer an out-of-walk supertype already gets — and a truer one than the bare `class Config` that dropping it printed, since a missing base reads as a claim that the class has no parent. PHP enums are not extracted as declarations at all, so an `enum … implements` clause is invisible — a missing declaration kind rather than a missing base. And a Scala `import` written inside a class or object body is not extracted at all (`surface::imports` reads only top-level ones), so a supertype it would have pinned is reported as ambiguous rather than resolved. Two more gaps are in the extractor rather than the resolver, and both cost an out-of-walk answer while leaving the in-walk one intact. A TypeScript or JavaScript `import * as api from './base'` keeps no local name for the module, so `class Child extends api.Root` cannot be recognised as naming `base.Root` when the target is outside the walk — inside it, the specifier decides through the on-demand rule. And a brace-form `import { Root as R } from './base'` records the module but not the item, so `class Other extends R` cannot be matched against an out-of-walk `Root` either; the rename path needs a specifier that ends at the item, which is Java's and Kotlin's shape rather than TypeScript's.
   - `--json` is the fifth rendering mode: any of the above commands accepts `--json` to serialise the same `Declaration` IR directly via `serde_json` into a versioned JSON schema, instead of formatting it as text. Add `--compact` for single-line output.

The `surface`, `deps`, `calls`, and `search` subsystems each have their own walk + render pipeline but use the same `Declaration` IR (and the same `file_filter`) under the hood. The call graph in particular extends `Declaration` with a `calls: Vec<CallSite>` field and `ParseResult` with `imports: Vec<ImportBinding>` so adapters can populate raw call-sites and import bindings during their existing tree walk; the resolver lives in `src/calls/resolve.rs`. See the dedicated wiki pages for their internals.

## CLI structure and the error contract

Every operation is an explicit subcommand — there's no implicit-default form. Bare `ast-bro` (no arguments at all) prints help to stdout and exits 0 — an orientation request, not a failed query.

Everything else follows one contract (issues #33/#36), implemented in `src/cli_error.rs` and applied by every subcommand:

- **Channel** — stdout carries results only. Every rejection, note, hint, and warning goes to stderr, which keeps `--json` output parseable without preprocessing and makes "stdout is empty" a reliable signal on its own.
- **Exit code** — `0`: the query ran; the answer may be legitimately empty ("this symbol genuinely has no callers"), and any qualification — a path that didn't resolve, a display cap, a depth cutoff — is reported as a `# note:` on stderr, so read the notes before treating exit-0 output as exhaustive. `2`: the query could not run as asked — no such path, no such symbol, unknown flag, missing argument, no paths after shell expansion — with nothing on stdout. `1`: internal failure (parse crash, unreadable cache).
- **Machine-readable form** — with `--json`, a rejection also emits an `ast-bro.error.v1` object on stderr (`{schema, command, kind, detail, hint}`, `kind` ∈ `no_input | path_not_found | symbol_not_found | unknown_flag | bad_argument | index_error`), so a consumer needs exactly one check instead of a per-subcommand table.
- **Unknown flags** — exit 2 with clap's error on stderr; when the flag exists on a sibling subcommand the message says which one (`--glob is a map flag`). Help on stdout is reserved for `--help`, which is a request for help — a rejected argument list is not a result.
- **Notes beside a real result** — qualifications of a delivered answer (partial path misses, truncation notes, ambiguity counts) stay exit 0, message on stderr, result on stdout.

The recovery rule an agent needs is one sentence: *stdout empty or exit non-zero → the call was wrong; read stderr; fix the call.*

The same reasoning applies to *coverage*, not just to truncation: an empty answer has to say how much ground it covers, or a caller cannot tell an honest zero from a scope that collapsed. `run` reports `no matches for "<pattern>" (N file(s) scanned)` on stderr with `files_scanned` in its JSON (silence there used to be indistinguishable from a `--glob` that matched three files); a multi-file `show` reports `N match(es) … in M of K file(s) searched` and puts `files_scanned` in the `symbol_not_found` envelope; `implements` already separated "no such type" (exit 2) from "type exists, zero implementors" (exit 0). And a rejected *path* offers a repair when one is verifiable on disk — the same basename found elsewhere, or the quoted form when an unquoted path with spaces was split into several arguments — implemented in [`src/path_repair.rs`](../src/path_repair.rs) and applied by `require_paths`, `require_path`, `show`, `find-related`, and the MCP path resolver. Verifiable is the operative word: an uncorroborated guess reads as authoritative and costs a second dead end, so no evidence means no hint.

Relatedly, capped output is never silent (issue #32): `callers`/`callees`/`impact`/`reverse-deps` headers report the true total when `--limit` trims the display — on stdout, not only as a stderr note, since stdout is where the result is read — JSON carries `total`/`truncated`, and `map --max-members` prints a `+N more` line for what it cut. Every section of a multi-section answer counts toward those numbers: `callers <Type>` implementations/constructions, `callees <Type>` ancestor groups, and the unresolved-call-site section each carry their own true total and share the display budget, so no section can pad `shown` and make a capped sibling read as complete. `--limit` therefore bounds *display*, not work: `callers`/`impact`/`reverse-deps` walk the full reverse cone to make the total exact, which is real work at `--depth 5` on a large repository.

`--depth` is the other way an answer comes back partial, and it needs its own field: a walk that ran out of depth and one that ran out of graph both just stop. Every depth-bounded command therefore reports which happened — `frontier_truncated` in JSON (top-level on `callers`, `callees`, `deps`, `reverse-deps`, and `trace`; per report on `impact`, whose direct sections are pinned to depth 1 whatever `--depth` says, so only the transitive cone can be cut short), plus a stderr note in text mode and the same line prepended to the response body on MCP, which has one channel. The flag is deliberately orthogonal to `truncated`: `truncated: false` with `frontier_truncated: true` says nothing was cut from the *display* and `total` itself counts only the part of the cone inside `--depth`. Only an edge into a node the walk never visited sets it — an edge back into visited territory is not "more to see", and the raise-`--depth` hint would be a lie. `callers`/`callees`/`impact` suppress the stderr note at depth 1, where "the callers have callers" is the norm rather than a qualification and a note firing on most queries trains the reader to skip it; the JSON flag is set at every depth. `trace` spends its flag differently: `found: false` alone reads as "these two symbols are not statically connected", so a capped search says "no static call path found within --depth N" instead of blaming a dynamic-dispatch boundary the evidence doesn't support.

`map` and `digest` are one command (issue #37): same walk, same `Declaration` IR, byte-identical `--json`. `map` exposes three orthogonal axes — detail (`--detail names|signatures|full`), visibility (`--no-private`, `--no-fields`, …), and scope (`--glob`, `--max-members`) — and `digest` is an alias for `map --preset digest` (`--detail names --no-private --no-fields --max-members 50`), with explicit flags overriding the preset. Detail below `full` also sheds doc comments from the JSON payload, which is routinely a third of its weight.

## MCP Server (`src/mcp/`)

`ast-bro mcp` runs the binary as a [Model Context Protocol](https://modelcontextprotocol.io) server so coding agents can invoke the same operations as native tools. The implementation is intentionally tiny:

- **Transport**: line-delimited JSON-RPC 2.0 on stdin/stdout, fully synchronous — no tokio, no extra dependencies. The cost is ~600 KB of binary (~1%) and zero overhead on the regular CLI commands, since none of the MCP code runs unless you invoke the `mcp` subcommand.
- **`src/mcp/protocol.rs`**: serde types for `Request`/`Response`/`RpcError` and the standard JSON-RPC error codes.
- **`src/mcp/tools.rs`**: declares nineteen tool schemas (`map`, `digest`, `show`, `implements`, `callers`, `callees`, `trace`, `surface`, `impact`, `context`, `squeeze`, `deps`, `reverse_deps`, `cycles`, `graph`, `search`, `find_related`, `index`, `run`) and dispatches `tools/call` into the existing `core::render_*` / `calls::*` / `surface::*` / `impact::*` / `context::*` / `deps::*` / `search::*` functions. Each tool maps 1:1 to a CLI subcommand and reuses its render logic byte-for-byte, so the JSON schemas are shared with the CLI's `--json` output. The defaults are shared the same way, from [`src/defaults.rs`](../src/defaults.rs): clap reads the constant (`default_value_t = defaults::LIMIT`), serde reads a thin function around it, and the schema interpolates it into the property description, so the number an agent is told is the number the tool applies.
- **`src/mcp/mod.rs`**: read loop, method routing (`initialize`, `ping`, `tools/list`, `tools/call`, `resources/list`, `prompts/list`), and panic-safe tool dispatch (panics are surfaced as `-32603 internal error` instead of taking the server down).

Tools are exposed in their text form by default — that's what the agent prompt is built around — with `json: true` available for any client that wants the structured payload.

## Adding a New Language

Adding a new language is incredibly straightforward due to the foundation provided by `ast-grep-language`.

1. Identify the target language from the `SupportLang` enum in `ast-grep` (e.g. `SupportLang::Cpp`). If not present, you'll need a native fallback — Markdown does this via `MarkdownLang` in `src/adapters/markdown.rs`, and SQL skips tree-sitter entirely with a regex parser in `src/adapters/sql.rs`.
2. Create a new `src/adapters/mylang.rs` file and `pub mod mylang;` it from [`src/adapters/mod.rs`](../src/adapters/mod.rs).
3. Implement the `LanguageAdapter` trait.
4. Write a `_walk_top` function to perform depth-first traversal of the `ast_grep_core::Node` children.
5. Identify AST kinds by matching `node.kind()` and retrieve source values using `node.field("name")` or slicing `src[node.range().start .. node.range().end]`.
6. Convert them to generic `Declaration` objects representing Classes, Functions, Fields, Interfaces, etc.
7. Wire your new adapter into the `parse_file_for_hook` routing match block in [`src/main_helpers.rs`](../src/main_helpers.rs). Languages that bypass `ast-grep` (Markdown, SQL) get a pre-`SupportLang` extension check at the top of that function.
